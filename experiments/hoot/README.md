# Hoot pull-based workflow spike

Isolated experiment; no Sweatpants or Tisyn production code was changed.

## Result

Hoot 0.9.0 can evaluate new Scheme source inside a prebuilt WASM interpreter,
yield effect descriptors using delimited continuations, and accept values from
the host to continue. The same probe passes in Node 22 and local workerd
2026-10-01. See `versions.txt`, `node-result.json`, and `workerd-result.json`.

Eight assertions cover:

1. Dynamic source yields a random request.
2. Supplying the host-recorded integer resumes into an ask request.
3. A fresh WASM instance emits the same initial descriptor.
4. Replaying the saved result restores the pending ask.
5. Supplying an answer finishes as `Ada:4`.
6. 100,000 interpreted tail calls finish without stack overflow.
7. A program-authored `syntax-rules` macro yields an effect.
8. That macro's suspended continuation resumes with the host's value.

A separate Node worker-thread probe runs an unbounded interpreted loop and
terminates its worker after 250 ms. This demonstrates external host containment,
not interpreter fuel. No workerd per-step instruction budget was established.

## Primitive

```scheme
(let ((n (effect "random" "1..6")))
  (let ((answer (effect "ask" "Your name?")))
    (string-append answer ":" (number->string n))))
```

`kernel.scm` returns two reflected procedures:

- `start(source)` -> multiple values `("effect", name, payload)` or `("done", value)`
- `next(result)` -> next effect or terminal value

`effect` aborts to a private prompt. The prompt handler saves its continuation
inside the WASM instance and returns the descriptor. `next` consumes the pending
continuation under a new prompt. It does not schedule work or invoke host I/O.
Only the original start continuation wraps the final result; wrapping every
resume would incorrectly turn the first terminal tag into the result.

A new interpreter receives source and previously accepted results. Continuations
are not serialized. The small host journal in `scenarios.mjs` is an explicit
fixture, not Sweatpants' actual journal authority. The random value is supplied
by that fixture, not generated by Hoot. Integration with real recorded effects
and process-loss recovery remains future work.

## Findings and constraints

- Runtime eval requires `-fruntime-modules` in Hoot 0.9.0. The runtime diagnostic
  suggesting `-g` did not accurately describe this CLI requirement.
- Runtime modules expand this prototype's main WASM from about 1 MB to
  5,766,441 bytes (1,292,092 bytes gzip in this build). Two helper WASMs and the
  roughly 53 KB reflection library are also required. Size is not optimized.
- Node's scenario run was about 0.5 s; local workerd about 0.4 s. These are single
  local observations including multiple fresh instances, not benchmarks.
- JS numbers arrive as inexact Scheme numbers. The probe bridges safe integers
  through BigInt and converts exact results back with a safe-range check.
- Evaluated string literals can be reflected mutable Scheme strings. The probe
  converts them through Hoot's string reflection API.
- `prepare-worker.py` makes a generated platform adapter: static WASM imports
  replace the browser/Node loader, and browser-style I/O avoids Node filesystem
  assumptions. No dynamic WASM compilation is needed in the Worker.
- This general Scheme evaluator is NOT an approved sandbox. The default user
  environment is broad; passing `effect` explicitly does not remove its other
  capabilities. The spike binds only localhost and evaluates fixed probe code.
- No static type inference, enum types, effect typing, instruction fuel,
  comprehensive JSON boundary, source validation, or production memory policy.
- No Cloudflare account deployment, DO integration, or production app change.

## Next decision

This validates Hoot as a runtime candidate, not a replacement recommendation.
The next useful experiment is a restricted environment plus an enforceable fuel
mechanism, followed by adapting the existing Sweatpants evaluation port. Keep
journal authority and effect execution outside WASM. Static typing can remain
an authoring/IR validation layer independently of this runtime choice.

## Follow-up: restricted capabilities and WASM fuel

The follow-up is isolated from the baseline above. `restricted.scm` evaluates
programs in a fresh environment importing an explicit list of syntax and pure
functions from `(scheme base)`. The injected `effect` function accepts only
`ask` and `random` and bounded string payloads. Source is limited to 12,000
characters. Runtime module lookup, imports, eval, filesystem procedures, and
FFI are not in the program environment. This is a deliberately small profile,
not general Scheme compatibility or a security audit.

`meter.scm` uses Hoot's WASM parser and assembler to instrument the compiled
interpreter. It adds an i64 fuel global, a decrement/check at every defined
function entry, and a decrement/check at every loop header. This build contains
19,556 functions and 169 loop headers. Exhaustion executes WASM `unreachable`;
it is not a Scheme exception or an authored callback. The host can set fuel
before each `start`/`next`, and must discard a trapped instance. The fuel export
is available to the JS host, not the Scheme environment. Offset-sensitive debug
sections are removed when rewriting instructions.

**Both Node and local workerd pass:**

- All eight baseline suspension/replay/tail-call/macro assertions.
- Eleven rejected capability attempts: file access, fuel mutation, eval,
  public/private module lookup, import, load, FFI, unauthorized effect name,
  function-valued effect payload, and a macro expanding to file access.
- Four exhaustion cases with 20,000 fuel units: infinite interpreted recursion,
  infinite macro expansion, list-allocation loop, and a runaway continuation
  after an Ask resume. Each traps at fuel -1.
- A fresh interpreter still computes 42 after the previous instance traps.

Rejection assertions require Hoot's SchemeQuitError with fuel remaining; an
unrelated JS error or fuel trap does not count as a capability rejection.
See `restricted-node-result.json` and `restricted-workerd-result.json`.

The ES-module error path exposed an upstream Hoot 0.9.0 reflection bug:
`for (attr in map)` uses an undeclared variable in the DWARF formatter.
`prepare-restricted.py` changes it to `for (const attr in map)` in generated
adapters. Without that fix, workerd reports a ReferenceError while formatting
an otherwise valid capability rejection. The original upstream runtime file
remains unchanged.

### What the result establishes—and what remains

This demonstrates host-controlled, deterministic *control-flow fuel* enforced
inside WASM on workerd. It is not Cloudflare's CPU-millisecond limit, nor a count
of every WASM instruction. Cloudflare documents that its configured CPU limits
are enforced on its deployed network, not local development:
https://developers.cloudflare.com/workers/wrangler/configuration/#limits

Fuel covers the main interpreter's functions/loops, including its reader and
macro expander. Helper WASMs and host imports are not instrumented. One native
operation can still consume variable CPU or memory; GC allocation, large
numbers/strings, and native host work need separate limits and review. Source
length alone does not bound expansion or output size. The tests are evidence
for this profile, not proof against all language/runtime escapes.

The follow-up below adds a bounded JSON bridge, poisoned handles, evaluation
budgets and a real Sweatpants journal integration. Native allocation limits and
production integration remain open. No Cloudflare deployment was changed.

## Real Sweatpants journal integration

`journal.scm`, `evaluation.ts`, and `runner.ts` now connect Hoot's suspended
continuations to Sweatpants' real durable tool driver and journal authority.
This is an isolated experiment; yo-tisyn's production evaluator is unchanged.

The frontend is explicitly Scheme. `SchemeEvaluationPort` has the same
open/advance/close lifecycle and `EvaluationStep` result as the Tisyn evaluator,
but accepts Scheme source. It does **not** compile Tisyn IR or claim equivalent
binding semantics. The experiment has its own program identity, fingerprinting
the WASM, reflection helpers, host bridge, dispatcher and bound tool contract.

```scheme
(let-syntax ((ask! (syntax-rules ()
                    ((_ prompt)
                     (effect "ask" (object (cons "message" prompt)))))))
  (let ((choice (effect "random"
                  (object (cons "choices" (array "rock" "paper" "scissors"))))))
    (let ((answer (ask! "Your name?")))
      (if (equal? (field answer "action") "accept")
          (object (cons "choice" choice) (cons "answer" answer))
          answer))))
```

The execution path is:

1. Durable Scheme tool opens a fresh metered WASM evaluator.
2. Scheme yields `random` with a JSON request. The host validates it and calls
   yo-tisyn's existing `randomValue`, which records the result in the authority.
3. Scheme receives that result through `next`, then yields `ask`.
4. The host invokes the real pinned Ask durable child. Its elicitation parks.
5. Scope cleanup closes the evaluation handle; no continuation is serialized.
6. A fresh authority restores the JSON snapshot. A fresh driver and WASM replay
   the source, consuming accepted random/tool results from the journal.
7. The resolved Ask result resumes Scheme, including the full typed reply and
   exchange message history. Scheme returns a JSON value.

### Verification

`__tests__/journal.test.ts` passes four tests:

- Independent journal snapshot/recovery scenarios for accept, decline and cancel.
  Each also recovers while the reply is still pending before resolving it.
- Bridge/lifecycle checks: JSON containers, Unicode and escaped strings, rejected
  procedures/duplicate keys/prototype keys, one-expression admission, terminal
  handle invalidation, fuel exhaustion before and after suspension, and a healthy
  fresh instance after failure.

The journal scenarios assert zero retained evaluation handles after parking,
new WASM instances during recovery, unchanged accepted journal prefixes, exactly
one random record, and no additional entropy calls on replay. The accepted
result's choice must equal the recorded outcome. These are actual authority and
tool programs; the only observation wrapper counts calls to real WebCrypto.

The bridge uses tagged vectors internally to distinguish JSON objects, arrays
and null. Host inputs are read as Scheme **data**, never evaluated. Reflected
procedures and other runtime objects cannot cross into the journal. Host
validation follows Sweatpants' canonical JSON rules and real tool schemas.

Budgets: 12,000 source characters, 65,536 JSON bytes, depth 32, 4,096 value nodes,
2,000,000 fuel per advance, 20,000,000 fuel per evaluator, and 256 yielded effects.
Every failed advance invalidates its handle. These are experimental bounds,
not tuned production defaults. JSON byte checks occur after reflection; they
do not cap WASM allocation or the cost of a single native operation.

### Next boundary

This proves a Scheme continuation can sit behind Sweatpants' existing durable
effect machinery. It does not yet prove model authoring quality, static Scheme
types, a deployed Worker integration, or a replacement for Tisyn. The next
useful comparison is the same small interactive workflow authored by a model
in each frontend, with the same host capabilities and recovery expectations.

## Model authoring comparison (2026-10-14)

`comparison/` runs real Haiku 5.5 authoring via the same provider adapter and
credential store as yo-tisyn. It verifies the outgoing reasoning effort is
`medium`. It does not use a mocked model or manually repair generated source.

The primary run is `comparison/results-2026-10-14T12-07-39.295Z/`. Each language
received two fresh-conversation trials for three requests: literal greeting,
three-round rock/paper/scissors with buttons and invalid-input handling, and a
name-badge review/edit loop. Both received the same Ask/Random contracts and
completion requirements, with compact frontend-specific language references.
No task solution or task-specific implementation example was supplied.

The profile is restricted Scheme versus Tisyn with a compact reference, not all
of Scheme versus the full production Tisyn prompt. In particular the current
Scheme environment omits standard `and`/`or`; some generated game sources use
these despite the advertised allowlist. This is a profile/admission issue as
well as a language-authoring comparison, and deserves a parity follow-up.

| Task (two initial trials each) | Scheme | Tisyn |
| --- | --- | --- |
| Literal greeting | 2/2 | 2/2 |
| Three-round game | 0/2 | 0/2 |
| Badge review and correction | 2/2 | 1/2 |
| Total | 4/6 | 3/6 |

A single repair with the durable execution diagnostic rescued none of the five
initial failures. That diagnostic is usually only `Durable program failed`;
it obscures parser details. Tisyn failures include wrong constructor arities
caused by misplaced parentheses; Hoot failures include unexpected closing
parentheses and unexpected EOF. These trials do not show a failed game strategy:
the games did not reach successful execution.

All replies in the acceptance harness cross a serialized authority snapshot and
a fresh evaluator. Checks include exact results, suggested buttons, random
record outcomes, scores, retained state, stop handling and evaluator cleanup.
The successful badge programs additionally pass 33 checks covering decline and
cancel at later questions and an unrecognized review reply. The harness itself
has a known-good greeting test for both runtimes.

The Scheme badge authored a reusable higher-order `with-reply` function using
lexical callbacks. The successful Tisyn badge authored an Ask helper returning
an `{ok,value}` / `{ok,status}` result and used explicit recursive state. Neither
was instructed to choose that abstraction. No first-attempt source in this run
used a local syntax macro.

Median first-attempt reported output tokens were 2,459 for Scheme and 6,376.5
for Tisyn; median source sizes were 1,734 and 1,269.5 characters respectively.
Provider output usage is not a source-token count. Timing/cost data are retained
in `metrics.json`; these small, sequential, cached requests are not a runtime
performance benchmark. Two trials per task are exploratory, not a statistical
language ranking.

An initial pilot with a 6,500-token ceiling completed both greetings but
truncated the first Tisyn game. `comparison/pilot.log` and the earlier result
folder retain that partial run. The primary run used 12,000 tokens for every
request and the same 120-second request timeout. Primary artifacts include
full prompts, returned source, provider usage, effort, diagnostics and successful
interaction traces. `.scm`/`.tisyn` files are untouched extracted model source.

`comparison/repair.ts` is a **separate diagnostic-feedback experiment**: it
branches from each initial failed source (not from its failed generic repair),
gives the actual parser/evaluator diagnostic, and permits one new model attempt.
Its outcomes are recorded separately in `diagnostic-repairs.json`; they do not
replace the primary scores above.

That experiment rescued one Scheme game and one Tisyn badge. Including successes
from the initial attempts, totals with one **diagnostic-guided** repair are
5/6 Scheme and 4/6 Tisyn. One Tisyn diagnostic repair exhausted the 12,000-token
ceiling; the other remaining game repairs still failed. This is a separate
repair branch, not two sequential attempts granted to the same conversation.

The repaired Scheme game then passed five additional full games, collectively
covering all nine player/computer move matchups. Each game also exercises an
invalid move, the three suggestion buttons, real recorded randomness, scoring,
snapshot recovery at every reply, and initial decline/cancel. See
`prs-audit.json`. No generated source was hand-edited to obtain these results.

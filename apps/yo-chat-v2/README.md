# Yo Chat v2

Living documentation of building a chat interface with Sweatpants v2 and TanStack Start.
The conversation is the application; tools are registered participants.

## Run

From the repository root (Node 24.22.0):

```sh
pnpm --filter yo-chat-v2 dev
pnpm --filter yo-chat-v2 build
pnpm --filter yo-chat-v2 preview
```

Open http://localhost:3000. Vite and TanStack Start own routing, server rendering, hydration and assets. `src/routes/__root.tsx` owns the document; `src/routes/index.tsx` redirects to the card-chat example; `src/router.tsx` constructs the router. The route tree is generated by Start.

The main example is `/chat/cards`: a model conversation with an inline `pick_card`
plugin, backed by v2 hosting and SQLite. `/chat/flight` adds the v1 flight-booking flow with sequential flight and seat
pickers. `play_tic_tac_toe` remains a future example.

## Start with the conversation

Follow these files for the main integration path:

1. `tools/pick-card.ts` authors the tool, its capabilities and elicitation.
2. `server/card-chat-program.ts` registers it with `createChatToolBinding` in a
   `defineChatProgram` conversation and installs the draw implementation in scope.
3. `server/chat-conversation.ts` owns shared conversation history and turn journals;
   `server/chat-run.ts` produces events and `server/chat-handlers.ts` adapts their
   stream to Start requests. `server/chat-demo.ts` describes the app-local policy.
4. `card-chat/CardChat.tsx` registers `defineToolUI` and places `ToolOutlet` inside
   the message tree. The conversation client owns delivery and reconnection.

This path does **not** construct a `createToolApplication` per tool. The chat host
already supplies each tool's child journal and owns advancement. The shared session
assembly is used underneath `createChatToolBinding`; normal chat authors need not
construct sessions themselves.

### Separate composition: a tool as durable RPC

`/examples/tool-rpc` hosts a single tool directly, without a chat/model loop.
Its `createToolApplication` commands, local Start adapter and local React hook are useful
for an approval form, wizard or independently callable tool that can pause for input.
It demonstrates another use of the same primitives, not a prerequisite for chat.
The `cards/`, `server/pick-card.ts`, `server/card-handlers.ts` and `/api/cards/$execution`
files belong to that standalone example.

The retired custom-server assembly lives in `packages/v2/acceptance/examples/chat-prototype` solely to preserve framework acceptance evidence. Its journeys do not test this Start app. Local SQLite data lives under ignored `data/` by default; model credentials remain server configuration.

## Server handlers

`src/routes/api.health.ts` defines `GET /api/health` with TanStack Start's
`createFileRoute(...).server.handlers`. It returns `{ "status": "ok" }` as JSON
and only checks that the app can serve requests; no external services are checked.
Add handlers by HTTP method on a file route. Each handler receives a standard
`Request` and returns a `Response`, including streaming response bodies when needed.
Start owns dispatch alongside page routes; no separate server router is needed.
The health route supports HEAD and uses ANY to return 405 for other methods;
without that fallback, Start can continue into page rendering.

## Design system

Use Astryx (`@astryxdesign/core`) components directly, imported from their individual entries. Use component props for behavior/layout and StyleX `xstyle` for application styling. The root shell uses Astryx Theme, VStack, HStack, Link and Text; the chat page uses Astryx Chat components, and the standalone example uses Card. The copied hand-written primitives have been removed.

Rosé Pine colors from yo-workflow live in `src/themes/rose-pine/rosePineTheme.ts`, extending Astryx’s neutral theme. The CLI prebuilds the theme for SSR on both dev startup and production builds. `src/astryx-themes.ts` is CLI-managed; `pnpm exec astryx theme add rose-pine` regenerates its registration. After editing theme source, run `pnpm theme:build` (or use the CLI’s `--watch` option).

`src/style.css` declares reset/base/theme cascade order and loads Astryx’s styles. Custom shell styles remain in StyleX. `AGENTS.md` contains the installed Astryx authoring guide; inspect components with `pnpm exec astryx component <Name>`. The installed release is beta; keep Core, CLI and the base theme on matching versions.

The root document links the complete base/theme stylesheet with Vite’s `?url` import so CSS blocks first paint in development too. It also links StyleX’s dev CSS endpoint; production StyleX rules are included in the built stylesheet. This avoids Start 1.149’s quoted-CSS extraction bug. Internal shell links compose Astryx Link with TanStack `createLink` for client navigation.

## Card-picker chat

`/chat/cards` recreates the v1 card-chat flow using the v2 assemblies and the
existing Astryx/StyleX shell: suggestion buttons, a message composer, streamed
assistant Markdown, a random hand inside a tool-call message, a retained selected
card, and follow-up conversation memory. The standalone picker lives separately at `/examples/tool-rpc`.
Conversations can be started and switched from the page. This tab's sessionStorage
keeps the conversation list and exact pending commands; SQLite owns accepted history.
Reload and switching only read, without provider credentials or implicit advancement.

The authoring path is `tools/pick-card.ts` → `server/card-chat-program.ts`
(`defineChatProgram` + `createChatToolBinding`) → the Start handlers at
`/api/card-chat/$thread`. Card draws are recorded effects. The server validates that
an answer was offered, checks descendant ownership/grants, and separates acceptance
from advancement. The browser registers a `defineToolUI` plugin and places its
`ToolOutlet` inside the conversation. Responses preserve accepted tool history; the
composer sends only new text, never a browser-supplied transcript.

The server selects Pi's OpenAI provider by default (`CHAT_PROVIDER`, `CHAT_MODEL`,
default `gpt-6.1-sol`). `OPENAI_BASE_URL` supports the CLI proxy; credentials belong
in the server environment (`OPENAI_API_KEY`), never client code or committed files.
The request-owned SSE stream uses AG-UI text/run event names and a `CUSTOM`
`card-chat-view` event for this application's validated detached snapshot. The run/text/custom projection comes from
`@sweatpan.ts/protocols-ag-ui`; this is not a general AG-UI client implementation. Provisional text
is replaced by accepted history when the command completes. Disconnect stops local
request work, not durable cancellation; interrupted/uncertain work remains visible
with explicit retry/check-status/continue actions. No automatic model retry is added.

### Run events are a stream

`server/chat-run.ts` supplies application commands and public views to the framework
`createAgUiRun` adapter. The card wrapper
`server/card-chat-run.ts` supplies card-specific policy. It uses the existing
runtime `Stream` and buffered signal; constructing it starts no work. The caller
explicitly owns production, and each reader pulls independently:

```ts
const run = createCardChatRun(runtime, openDatabase, sampling, thread, command);
const owner = runtime.start(() => run.run());
const body = createReadableStream(runtime, run.events());
// A second body can consume run.events() without starting a second execution.
// The owner must eventually be awaited or explicitly cancelled.
```

The Start handler adapts that stream to SSE. Each browser `.read()` requests one
runtime stream item; waiting readers wake from the existing signal, without polling.
Slow readers do not stall execution, and cancelling one subscription does not cancel
production. The route deliberately adds request ownership: cancelling its response
cancels and joins the owner. This remains request-owned, not background execution.

The buffer retains this attempt's events until its run object is released. Readers
can resume with `run.events(offset)` while that object is retained; offsets count
source events and are neither durable journal cursors nor HTTP resume tokens. There
is no server run registry or cross-process notification service. GET reconstructs
accepted state from SQLite and streams a fresh snapshot without starting the model.
It does not recover unaccepted text deltas or follow another request's live work.

A command attempt ends when hosting completes or parks for input; `RUN_FINISHED`
ends that request stream, not necessarily the durable turn. Answering starts another
explicit attempt for the same turn. A full turn-following stream across parked
requests still needs an owner/notification and retention policy. This experiment
establishes the stream consumption boundary without inventing that policy.

When public questions remain open, `RUN_FINISHED.outcome` has type `interrupt` and
includes every answerable question. Interrupt IDs are the public question IDs;
`metadata["sweatpants/question"]` carries the same root, execution, resolution grant,
effect and input as the custom view. GET reconstructs these interrupts from SQLite.
Answered, blocked and cancelled questions are excluded. With no open questions the
terminal event omits `outcome`; it does not assert objective success. Answers still
use the existing validated command route, not AG-UI resume input. The metadata is
public presentation data, not participant authentication or answer authority.

Acceptance covers two readers, a slow reader, disconnection, same-attempt offset
resume, persisted reconstruction and pre-aborted requests under both runtimes.
The promoted adapter retains the memory-only buffer for one attempt. It is unbounded;
a longer-lived run service still needs an explicit retention and ownership policy.

The acceptance journey uses the actual React composer and picker, SSE handlers,
SQLite reopen and both native runtimes with a scripted model exchange. It covers
hand retention, rejection of unoffered cards, lost answer confirmation, exact-command
retry, restored answered rendering, follow-up memory and conversation switching.
Live provider behavior and visual browser layout are not established by that test.
This remains a local demo: no authenticated ownership, cross-device thread catalog,
stop/interrupt-and-queue policy, inspector or multi-tab coordination is included.

## Flight-booking chat

Open `/chat/flight`, also linked in the main navigation. This ports v1's Flight Booking
page: NYC–LA and SFO–Seattle suggestions, a list of three simulated flights, a seat
map with unavailable seats, a recorded travel tip, and a simulated ticket. There is
no real booking or payment. The existing Astryx chat layout is shared with card chat.

The authoring path is:

- `tools/book-flight.ts`: one tool with two sequential elicits and search, seats,
  travel-tip and ticket capabilities. It validates selections against offered data.
- `flights/flight-ui.tsx`: one typed renderer registration with flight and seat
  components. Accepted choices remain visible after reload.
- `server/flight-chat-program.ts`: model catalog, prompt, result formatting and
  scoped installs. Search/seats/ticket use the ported v1 demo services. The travel-tip
  capability uses the existing sampling interface with no tools and records its result.
- `flights/FlightChat.tsx`: page copy, suggestions and plugin registration, with a
  separate endpoint and browser storage namespace.

Both demos now use the same `chat/client.ts`, `chat/ChatDemoPage.tsx`,
`server/chat-conversation.ts`, `server/chat-view.ts`, `server/chat-run.ts` and
`server/chat-handlers.ts`. The shared question envelope carries recorded program
and effect IDs; the client no longer assumes every question is a card. Domain input
decoding and context-dependent answer validation remain explicit page policies.
Flight conversations use a separate namespace in the existing SQLite turn table;
the existing card namespace and program identity are preserved.

The flight acceptance journey runs the actual React page and shared handlers under
both runtimes. It reloads between pickers, rejects an unoffered flight and an occupied
seat, loses the final response, retries the same answer, and verifies one search,
one seat-map load, one recorded tip and one ticket delivery. Question identities and
selected controls survive reopening. It also verifies isolation from card chat.
This is simulated service/reopen evidence, not live provider or crash-durability proof.

The extraction remains app-local. In particular, `chat-view.ts` is the existing
success-path journal projection shared across two demos, not the full R2 protocol
reader: retained cancellation traversal and sampling-denial diagnostics are still
pending. Full-turn live following across requests and durable stream cursors also
remain future work; adding this page does not claim those guarantees.

## Standalone picker: durable RPC

`/examples/tool-rpc` demonstrates start, pick a card, and view the result without a model.
`src/cards/CardPicker.tsx` uses Astryx buttons, the local `useStandaloneTool` hook and a registered `cardUI`
plugin. Domain schemas live in `cards/contracts.ts`. The authored tool declaration
currently enters the browser bundle; code splitting is deferred. Database and
server assembly imports remain in server modules.

This tab retains its execution ID in sessionStorage before starting. A choice retains
the exact card and resolution grant before sending an answer. Until its outcome is
confirmed, all choices remain visible but disabled and “Retry same answer” resends that command.
“Check status” only reads. An uncertain start retries the same execution ID. Reloading
reads the server's state, restores a pending choice, or shows the completed result;
it never automatically submits an answer. “Pick another card” creates a new execution
only after the current one is terminal. Closing the tab discards this local resume
pointer; it does not cancel or delete the server's execution.

Unmount aborts this component's HTTP work and ignores late responses, including storage
updates. This is local teardown, not durable cancellation. The demo handles one active
interaction per tab and does not provide account-level history or multi-device recovery.

`start-pick-card-ui.acceptance.test.tsx` exercises the real React/Astryx picker, transport,
Start handlers and SQLite through simulated HTTP on both native runtimes. It covers
reloads, lost start/answer responses, duplicate receipts, retained pending answers and
late responses after unmount. It is jsdom/in-process evidence, not a visual browser test.

## Standalone tool backend

`src/tools/pick-card.ts` authors the tool with `defineTool`, `defineEffect` and `ctx.elicit`.
`src/server/pick-card.ts` supplies the SQLite opening policy.
`src/standalone/server.ts` binds `createToolApplication` commands to Start and defines this example's JSON view. The shared tools assembly owns admission, acquisition, recovery,
participant routing and validated answer ingress. Its scoped command API is also
available directly, without HTTP. Start routes only validate the HTTP envelope and
own the native request task.

Use one caller-generated UUID for an invocation at `/api/cards/<execution>`:

- `POST`: submit `{ "input": {} }` to admit and advance to the card question. Reusing the ID resumes the same invocation.
- `GET`: read the retained view without advancing. An unadmitted ID returns 404.
- `PUT`: submit `{ "grant": { "requestId": "…", "resolutionId": "…" }, "outcome": { "ok": true, "value": { "rank": "Q", "suit": "hearts", "display": "Q♥" } } }` using `question.grant` and an offered card object from the waiting view. It returns an acceptance receipt, duplicate flag and completed view.

Identical answer retries recover the receipt. Wrong grants and conflicting answers reject;
they do not select a new card. Malformed command envelopes return 400 and foreign-origin writes return 403. Domain validation and journal/runtime failures propagate through Start’s error boundary. A failed or lost
response does not prove that nothing was committed: reread or retry the identical command.
Acceptance and advancement are separate durable steps; POST or an identical PUT can finish
advancement after interruption. GET never does that work automatically.

The Node adapter in `src/server/cards.ts` selects Effection and opens a fresh database
connection per application command. Each command scope closes its connection before
returning; the HTTP handler also joins its native task cleanup. A disconnected request may stop local advancement; the
journal retains any committed progress. No background task or process-local workflow is
needed while the tool waits for input.

Storage defaults to `data/yo-chat-v2.sqlite`, relative to the app working directory;
set `YO_CHAT_DATABASE` to select another file. This is a local demo with no authenticated
user/session ownership yet; execution IDs and resolution grants are not authentication.
The data is separate from the retired prototype, with no schema migration promise.

`start-pick-card.acceptance.test.ts` exercises these handler functions under Effect and
Effection with real temporary SQLite files: reopened connections, repeated start, exact
answer retry, concurrent duplicate delivery, foreign grants, conflicting values, invalid
input, request cancellation and connection disposal. This is in-process acceptance, not
process-crash or deployment evidence.

The picker uses the application-local `useStandaloneTool(pickCard, { endpoint: "/api/cards" })` and
`defineToolUI(pickCard, { chooseCard: ... })` for typed input and `respond(card)`.
`ToolUIProvider` registers that plugin and `ToolOutlet` displays the question.
The selected card remains visible after acceptance and reload. The local client
composes `createChatClient` observation with explicit HTTP, identity, retention and retry
policy; the component owns presentation.
The authored declaration currently enters the browser bundle. Contract projection is
not code splitting. This example's JSON adapter requires JSON-compatible inputs,
answers and results, and exposes only the direct root question, not a chat tree.

This increment uses the `yo-chat:pick-card:v3` sessionStorage key and raw execution
IDs in SQLite. The previous card-specific demo used a different
key and journal prefix; those local demo interactions are not migrated.

### Composition boundaries in the standalone example

- `standalone/server.ts` uses `createToolApplication` for commands and an explicitly
  scoped `journal.read()` for history projection. It consumes the existing
  journal reader while the connection is open; all returned view data is detached.
  The domain application's ordinary `read` has no renderer-specific history policy.
- `standalone/client.ts` uses `createChatClient` for observation and command forwarding.
  It explicitly reads after confirmed commands. Saved execution IDs, exact pending
  answers, abort signals and retry controls are this example's policy.
- `standalone/protocol.ts` and `contracts.ts` define local JSON validation. The existing
  wire/storage version strings are retained for local saved interactions; they are
  not framework exports or a supported general-purpose tool protocol.
- `standalone/use-standalone-tool.ts` owns one local client per mount. Shared React UI
  registration (`defineToolUI`, `ToolUIProvider`, `ToolOutlet`) remains independent of
  that ownership choice and also works in the conversation example.

`standalone-tool.acceptance.test.ts` exercises this local assembly with sequential,
schema-transformed questions; the existing card UI/HTTP journeys retain reload,
uncertain-delivery and scope-disposal evidence. The tools, chat-client and React
packages expose no `ToolHttp*`, `createToolHttpHandlers`, `createToolClient` or `useTool` APIs.

### One card tool, two hosts

`tools/pick-card.ts` returns `{ card: PlayingCard }` in both chat and the standalone
RPC example. Both hosts install `server/card-capabilities.ts` and both pages register
`cards/card-ui.tsx`. Only the chat program translates the result into model-facing text;
its model parameter schema is derived from the tool's Zod input schema.
Standalone GET opens an owned journal reader and detaches its observation before
closing the connection. It does not construct a tool session or run `configure`.

This changes the demo's persisted protocol: the shared tool and conversation program
now use revision 2, and browser storage uses fresh namespaces. Previous demo sessions
are not migrated or replayed under the new definitions; use a new conversation/picker.

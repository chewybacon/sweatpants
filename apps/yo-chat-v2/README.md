# Yo Chat v2

A fresh TanStack Start base for living documentation of Sweatpants framework integration.

## Run

From the repository root (Node 24.22.0):

```sh
pnpm --filter yo-chat-v2 dev
pnpm --filter yo-chat-v2 build
pnpm --filter yo-chat-v2 preview
```

Open http://localhost:3000. Vite and TanStack Start own routing, server rendering, hydration and assets. `src/routes/__root.tsx` owns the document; `src/routes/index.tsx` is the home page; `src/router.tsx` constructs the router. The route tree is generated by Start.

The first server-side tool is `pick_card`, backed by v2 hosting and SQLite. Its React interaction is next; there is no model or chat loop yet. `book_flight` and `play_tic_tac_toe` will follow as progressively richer public-API examples.

The retired custom-server assembly lives in `packages/v2/acceptance/examples/chat-prototype` solely to preserve framework acceptance evidence. Its journeys do not test this Start app. Existing ignored `data/` and `.env.local` files are preserved but unused by this base.

## Server handlers

`src/routes/api.health.ts` defines `GET /api/health` with TanStack Start's
`createFileRoute(...).server.handlers`. It returns `{ "status": "ok" }` as JSON
and only checks that the app can serve requests; no external services are checked.
Add handlers by HTTP method on a file route. Each handler receives a standard
`Request` and returns a `Response`, including streaming response bodies when needed.
Start owns dispatch alongside page routes; no separate server router is needed.
The health route supports HEAD and uses ANY to return 405 for other methods;
without that fallback, Start can continue into page rendering.

## Design system

Use Astryx (`@astryxdesign/core`) components directly, imported from their individual entries. Use component props for behavior/layout and StyleX `xstyle` for application styling. The root shell uses Astryx Theme, VStack, HStack, Link and Text; the home page uses Heading and Card. The copied hand-written primitives have been removed.

Rosé Pine colors from yo-workflow live in `src/themes/rose-pine/rosePineTheme.ts`, extending Astryx’s neutral theme. The CLI prebuilds the theme for SSR on both dev startup and production builds. `src/astryx-themes.ts` is CLI-managed; `pnpm exec astryx theme add rose-pine` regenerates its registration. After editing theme source, run `pnpm theme:build` (or use the CLI’s `--watch` option).

`src/style.css` declares reset/base/theme cascade order and loads Astryx’s styles. Custom shell styles remain in StyleX. `AGENTS.md` contains the installed Astryx authoring guide; inspect components with `pnpm exec astryx component <Name>`. The installed release is beta; keep Core, CLI and the base theme on matching versions.

The root document links the complete base/theme stylesheet with Vite’s `?url` import so CSS blocks first paint in development too. It also links StyleX’s dev CSS endpoint; production StyleX rules are included in the built stylesheet. This avoids Start 1.149’s quoted-CSS extraction bug. Internal shell links compose Astryx Link with TanStack `createLink` for client navigation.

## Pick a card backend

`src/tools/pick-card.ts` authors the tool with `defineTool`, `defineEffect` and `ctx.elicit`.
`src/server/pick-card.ts` composes tool acquisition, recovery, hosted participant waiting,
typed answer ingress and the SQLite journal. Existing guest retention owns capabilities
through registration; the host is disposed when it returns. Start routes remain thin.

Use one caller-generated UUID for an invocation at `/api/cards/<execution>`:

- `POST`: admit and advance to the card question. Reusing the ID resumes the same invocation.
- `GET`: read the retained view without advancing. An unadmitted ID returns 404.
- `PUT`: submit `{ "grant": { "requestId": "…", "resolutionId": "…" }, "card": "queen-of-hearts" }` using the grant from the waiting view. It returns an acceptance receipt, duplicate flag and completed view.

Identical answer retries recover the receipt. Wrong grants and conflicting answers reject;
they do not select a new card. Schema errors return 400 and foreign-origin writes return 403. Journal/runtime failures propagate through Start’s error boundary. A failed or lost
response does not prove that nothing was committed: reread or retry the identical command.
Acceptance and advancement are separate durable steps; POST or an identical PUT can finish
advancement after interruption. GET never does that work automatically.

The Node adapter in `src/server/cards.ts` selects Effection and opens a fresh database
connection per request. Each handler awaits its runtime task (including scoped cleanup)
before closing that connection. A disconnected request may stop local advancement; the
journal retains any committed progress. No background task or process-local workflow is
needed while the tool waits for input.

Storage defaults to `data/yo-chat-v2.sqlite`, relative to the app working directory;
set `YO_CHAT_DATABASE` to select another file. This is a local demo with no authenticated
user/session ownership yet; execution IDs and resolution grants are not authentication.
The data is separate from the retired prototype, with no schema migration promise.

`start-pick-card.acceptance.test.ts` exercises these handler functions under Effect and
Effection with real temporary SQLite files: reopened connections, repeated start, exact
answer retry, concurrent duplicate delivery, foreign grants, conflicting values, invalid
input, request cancellation and connection disposal. This is in-process acceptance, not
process-crash or deployment evidence.
